I.Tổng quan & định hướng sản phẩm

1.1. App là gì

  • App mobile bằng Flutter, build ra cả Android và iOS.
  • Loại app: quản lý thông tin nhiều hệ thống (system info management) — có đăng nhập, dữ liệu lưu trên SQL online qua backend API. App không kết nối thẳng vào database.
  • Định hướng sản phẩm: theo mô hình Splunk Mobile — app SIEM di động, tổng hợp log/cảnh báo từ nhiều nguồn để xem trên điện thoại.

1.2. Phạm vi chức năng đã chốt (không tự ý mở rộng)

Chỉ đúng 3 chức năng chính theo phạm vi Splunk Mobile thật — không thêm quản lý user, không thêm cấu hình nguồn, không thêm thao tác xử lý sâu vào hệ thống:

Chức năngPhạm vi đã chốt
DashboardsChỉ XEM (không tạo/sửa trên app) — nhiều panel (chart/KPI/table) hiển thị dữ liệu có sẵn từ backend
Alerts1 alert = 1 sự kiện/log từ 1 nguồn cụ thể, nhóm hiển thị theo nguồn. Chỉ xem + lọc theo mức độ/nguồn — không có trạng thái đã đọc/đã xử lý (acknowledge)

2.2.b. Vì sao chọn từng lựa chọn — trả lời câu hỏi "sao không dùng X"

Mỗi hạng mục ở bảng trên giải quyết đúng 1 vấn đề cụ thể. Không chọn theo trend, mà theo bài toán thực tế app này gặp phải:

* Riverpod — quản lý state + DI trong 1 cơ chế duy nhất

  • Vấn đề cần giải: khi dữ liệu đổi (kết quả API, trạng thái đăng nhập...), phải tự động cập nhật đúng phần UI liên quan — không gọi setState rải rác thủ công khắp nơi. Đồng thời cần 1 nơi cung cấp instance dùng chung (Dio, token storage...) cho nhiều màn hình mà không tạo lại.
  • Vì sao Riverpod, không phải Provider/Bloc/GetX: không phụ thuộc BuildContext (khác Provider gốc), bắt lỗi kiểu dữ liệu ngay lúc biên dịch nhờ code generation (@riverpod), và quan trọng nhất — đóng luôn vai trò DI. Nhờ vậy project không cần thêm get_it chạy song song 2 cơ chế "cung cấp instance" khác nhau — mỗi Provider vừa là state, vừa là nơi expose dependency.

Ví dụ thật trong app: apiClientProvider (core/network) tạo đúng 1 instance Dio, mọi datasource (auth, alerts...) ref.watch lấy lại đúng instance đó — không ai tự Dio() riêng.

  • Cơ chế "tự động cập nhật" hoạt động thế nào: Provider chỉ giữ 1 giá trị (state) và tự thông báo cho bất kỳ ai đang ref.watch nó khi giá trị đó đổi — không cần tự viết code "báo cho X biết". Ví dụ trong AuthController, chỉ cần gán state = AuthAuthenticated(user); Riverpod tự lo việc GoRouter (qua refreshListenable) và mọi widget đang watch AuthState sẽ tự rebuild — không có dòng code nào gọi thẳng "báo cho router" hay "báo cho UI".
  • Vì sao có 2 file .dart và .g.dart đi cùng cặp: bạn chỉ viết 1 hàm/class bình thường kèm annotation (@riverpod) và dòng part 'ten_file.g.dart';. Chạy dart run build_runner build (hoặc watch -d để tự sinh lại mỗi lần lưu) sẽ đọc cú pháp (tên hàm, kiểu trả về, annotation — không đọc hiểu logic bên trong) rồi tự sinh ra file .g.dart chứa class Provider đầy đủ tương ứng. File này luôn có dòng // GENERATED CODE - DO NOT MODIFY BY HAND — không bao giờ sửa tay, vì lần build sau sẽ ghi đè mất.

* Dio — gọi API có interceptor, không lặp code xác thực

  • Vấn đề cần giải: mọi request tới backend (trừ login) đều cần đính kèm access token vào header. Nếu dùng http package thuần, phải tự thêm header thủ công ở từng nơi gọi API — dễ quên, khó sửa đồng loạt.
  • Vì sao Dio: có cơ chế interceptor — 1 lớp trung gian chạy trước mọi request. App này dùng đúng 1 AuthInterceptor (core/network) tự đọc token từ secure storage và gắn Authorization: Bearer ... vào mọi request, viết 1 lần, áp dụng cho toàn bộ datasource. Đây là cơ chế thực tế đang chạy (xem luồng 3.3.a) — không phải lý thuyết.

* go_router — điều hướng gắn liền trạng thái đăng nhập

  • Vấn đề cần giải: phải tự động đẩy người dùng về màn Login nếu chưa đăng nhập, và ngược lại đẩy vào Home nếu đã đăng nhập — không để người dùng tự gõ URL vòng qua màn cần bảo vệ.
  • Vì sao go_router: khai báo toàn bộ route ở 1 chỗ (app_router.dart), có cơ chế redirect chạy lại mỗi khi 1 Listenable báo thay đổi — ghép thẳng với AuthState từ Riverpod qua refreshListenable (chi tiết cơ chế này ở sơ đồ 3.2.c). Không cần tự viết logic "check đăng nhập" lặp lại ở đầu mỗi màn hình.

* Drift — cache dữ liệu quan hệ (chưa dùng tới)

  • Vấn đề dự kiến giải quyết: app SIEM cần xem được alert/log ngay cả khi mất mạng tạm thời, hoặc cache dữ liệu có quan hệ (nguồn ↔ nhiều alert) để không phải gọi lại API liên tục. shared_preferences chỉ hợp với dữ liệu đơn giản dạng key-value (1 cờ bật/tắt), không hợp để lưu danh sách có cấu trúc.

Hiện chưa thêm vào project — phần đã code (Alerts) mới dừng ở gọi API trực tiếp mỗi lần mở tab, chưa có nhu cầu cache offline. Sẽ thêm khi feature thật sự cần (ví dụ: xem lại Alerts cũ khi mất mạng).

* Widgetbook — xem thử component độc lập, tách khỏi app thật

  • Vấn đề cần giải: nếu sửa 1 component dùng chung (ví dụ AppButton, SourceGroupCard) mà muốn xem kết quả, cách thông thường là chạy cả app thật, đăng nhập, điều hướng tới đúng màn hình chứa nó — chậm và vướng nhiều bước không liên quan tới component đang sửa.
  • Vì sao Widgetbook: tạo 1 entrypoint riêng (main_widgetbook.dart, hoàn toàn tách khỏi main.dart — không có AuthState, không có backend thật) hiển thị catalog toàn bộ component qua các file *.usecase.dart. Chạy bằng flutter run -t lib/main_widgetbook.dart -d chrome, xem/thử component ngay lập tức mà không cần đăng nhập hay điều hướng.

Đây là lý do quy tắc 8 (CLAUDE.md) bắt buộc: mỗi component/theme mới phải có 1 use case Widgetbook trước khi ghép vào feature thật — đảm bảo component đã đúng hình dạng/hành vi độc lập trước khi mang vào ngữ cảnh phức tạp hơn. Toàn bộ 21 use case hiện có (mục 2.3) đã pass bước này — nhưng như mục 4.2 cho thấy, pass Widgetbook không đồng nghĩa hết bug hành vi khi ghép vào màn hình thật.

4 quy tắc trọng tâm (đủ để hiểu kiến trúc khi trình bày):

  1. core/auth/ chỉ chứa logic (AuthService, AuthState) — không đặt UI. Toàn bộ giao diện đăng nhập nằm ở features/auth/presentation/.
  2. Mọi instance dùng chung (Dio, token storage...) expose qua Riverpod Provider ngay trong module sở hữu nó — nơi khác ref.watch, không tự khởi tạo lại.

  4. Thứ tự dựng UI bắt buộc: theme/token → component dùng chung → ghép màn hình. Không hardcode số/màu trong component.

2.4. Vì sao không có file .ini/.config trong lib/?

Mục đích thường thấy của .ini/.config (PHP, .NET, C/C++ native...): file text riêng nằm cạnh chương trình đã biên dịch, chương trình tự mở ra đọc lúc đang chạy (runtime) — gồm các vai trò quen thuộc: khai báo dependency, cấu hình theo môi trường (base URL, timeout...), connection string tới database, transform cấu hình theo môi trường build (debug/release), version/tên app, quyền/permission.

Đổi lại: đổi giá trị không cần build lại app, nhưng gõ sai tên key chỉ phát hiện lúc chạy, có khi không phát hiện luôn.

Dart chọn ngược lại: cấu hình viết bằng code Dart có kiểu dữ liệu (lib/core/config/app_config.dart), trình biên dịch "đóng băng" giá trị vào app lúc flutter build — gõ sai field báo lỗi ngay lúc build, đổi lại muốn đổi giá trị phải build lại.

// lib/core/config/app_config.dart — đây là "config.ini" của project này class AppConfig { final String apiBaseUrl; static const AppConfig dev = AppConfig(apiBaseUrl: 'http://10.0.2.2:3000'); }

Đối chiếu từng vai trò của .ini/.config với file/thư mục tương ứng trong project này:

2.5. Pipeline xây dựng 1 feature mới (bắt buộc theo đúng thứ tự)

Áp dụng cho mọi feature — không nhảy thẳng vào code UI khi chưa xong bước 1–2:

1. Chốt kiến trúc + stack + cây thư mục → đã xong 1 lần cho toàn app 2. Thảo luận chức năng → feature cho làm được gì, phạm vi tới đâu (KHÔNG suy luận từ ảnh tham khảo/component có sẵn) 3. Xác định màn hình cần có → dựa trên bước 2, không đoán theo giao diện 4. Đối chiếu danh mục component → shared/widgets/ đã đủ chưa 5. Xây dựng màn hình thật → model → datasource → repository → state/controller → UI ghép component có sẵn

Bài học rút ra: 18 component ban đầu được code dựa theo ảnh tham khảo trước khi thảo luận chức năng kỹ — đối chiếu lại vẫn khớp gần hoàn toàn, nhưng không phải thứ tự nên lặp lại. Feature Alerts là ví dụ đầu tiên làm đúng thứ tự 5 bước này từ đầu.

III.Các luồng dữ liệu chính

3.1. Nguyên tắc chung: luồng nào cũng đi qua đúng 4 lớp

Mọi luồng dữ liệu trong app — dù là đăng nhập hay xem Alerts — đều đi qua đúng thứ tự 4 lớp cố định (quy tắc kiến trúc ở Phần II.3), không lớp nào được nhảy cóc lớp nào:

UI (screen) → State/Controller (Riverpod) → Repository → Remote Datasource (Dio) → Backend

UI không bao giờ gọi thẳng Datasource; State không bao giờ tự gọi Dio. Đây là lý do khi đổi từ mock sang API thật (như Alerts vừa làm), chỉ cần sửa đúng 1 file Datasource — Controller, Repository, UI không đổi gì.

3.2. Luồng đăng nhập

3.2.a. Đăng nhập thành công

LoginScreen (nhập email/password, bấm nút) → LoginFormController.submit() [state riêng: isSubmitting, errorMessage] → AuthController.login() [core/auth — sở hữu AuthState toàn app] → AuthRepository.login() [lớp duy nhất được gọi từ state/UI] → AuthRemoteDatasource.login() [gọi Dio: POST /auth/login] → Backend: so bcrypt.compare(), query Postgres bảng users ← trả {accessToken, refreshToken, user} → SecureTokenStorage.saveTokens() [lưu 2 token vào bộ nhớ mã hóa] ← trả về User → AuthState chuyển thành AuthAuthenticated(user) → GoRouter (refreshListenable lắng nghe AuthState) tự redirect sang "/" → DashboardScreen hiển thị "Xin chào, {user.name}"

3.2.b. Đăng nhập sai / lỗi mạng

AuthRemoteDatasource ném DioException (401 "Sai email hoặc mật khẩu", hoặc lỗi kết nối) → LoginFormController bắt lỗi, đọc message thật từ response backend → hiển thị lên UI, KHÔNG đổi AuthState (vẫn ở màn login)

3.2.c. Sơ đồ: AuthState quyết định màn hình như thế nào

Điểm mấu chốt: AuthController là nơi duy nhất tạo ra AuthState, GoRouter.redirect() là nơi duy nhất đọc nó để chọn màn hình — hai bên chỉ nói chuyện qua đúng 1 sợi dây: refreshListenable.

3.2.d. Mở lại app sau khi đã từng đăng nhập

AuthController.build() → gọi _restoreSession() → AuthRepository.hasValidSession() → đọc access token đã lưu trong secure storage → nếu KHÔNG có token → AuthState = Unauthenticated → GoRouter redirect về /login → nếu CÓ token → giữ Initial (TODO: gọi GET /auth/me để lấy lại User đầy đủ)
Còn thiếu: app hiện chỉ kiểm tra "có token hay không", chưa gọi GET /auth/me để khôi phục thông tin User khi mở lại app. Endpoint đã có sẵn ở backend, chỉ chưa được gọi từ phía app — xem Phần IV.

3.3. Luồng xem Alerts (đã nối API thật)

3.3.a. Tải danh sách khi mở tab Alerts

AlertsScreen mở lên → AlertsController.build() [AsyncNotifier] → AlertsRepository.getAlerts() [lớp duy nhất state được gọi] → AlertsRemoteDatasource.getAlerts() [gọi Dio: GET /alerts] → AuthInterceptor tự gắn "Authorization: Bearer <accessToken>" → Backend: authenticate middleware verify JWT → SELECT * FROM alerts ORDER BY created_at DESC ← trả { alerts: [...] } (JSON) ← List<Alert> (đã parse qua Alert.fromJson) → _allAlerts lưu trong AlertsController, state = {} (bộ lọc rỗng = hiện hết) → AlertsScreen đọc controller.filteredGroups (đã lọc + group theo sourceName) → dựng danh sách SourceGroupCard, mỗi card 1 nguồn

Điểm quan trọng: AlertsController.state không phải là danh sách alert — nó là bộ lọc severity đang chọn. Danh sách alert gốc giữ riêng trong field _allAlerts, còn filteredAlerts/filteredGroups là getter tính lại mỗi lần build. Quyết định này giúp lọc theo severity không cần gọi lại API.

3.3.b. Lọc theo mức độ (High/Medium/Low)

Bấm chip "High" trên AppBar → AlertsController.toggleSeverity(AlertSeverity.high) → state = state ∪ {high} (hoặc trừ ra nếu đang chọn, logic OR — chọn nhiều severity cùng lúc) → AlertsScreen tự rebuild (ref.watch) → gọi lại filteredGroups (lọc client-side, KHÔNG gọi API lại) → danh sách chỉ còn nhóm/alert khớp severity đã chọn

3.3.c. Tìm kiếm + xem chi tiết 1 alert

Bấm icon 🔍 trên AppBar → SearchDialog.show() nhận List<String> dạng "title — sourceName" (đã ghép sẵn) → gõ từ khóa → normalizeForSearch() bỏ dấu + viết thường, lọc client-side → chọn 1 kết quả → Navigator push AlertDetailScreen(alert: alerts[index]) [Alert được truyền thẳng qua constructor — KHÔNG gọi lại API, vì GET /alerts đã trả đủ field cho cả list và detail trong 1 lần gọi]

Quyết định đã chốt: không thêm GET /alerts/:id riêng — giữ đúng kiến trúc hiện tại, ít việc hơn, vì response của GET /alerts đã đủ dữ liệu cho màn chi tiết.

3.3.d. Component đã chốt ghép vào màn hình

Đây là danh mục đã ghép thật vào AlertsScreen/AlertDetailScreen — không phải danh sách component có sẵn trong catalog, xem đúng vị trí từng cái:

3.3.e. Lỗi khi tải danh sách

AlertsRemoteDatasource ném DioException (401 hết hạn token, mất mạng, backend lỗi...) → AlertsController.build() ném lại lỗi → state = AsyncError → AlertsScreen switch sang nhánh AsyncError → hiện ErrorStateView + nút "Thử lại" → bấm "Thử lại" → ref.invalidate(alertsControllerProvider) → build() chạy lại từ đầu

Đây đúng là lỗi thật đã gặp khi test: access token hết hạn (15 phút) sau khi đăng nhập từ trước, gọi GET /alerts trả 401 → UI hiện đúng thông báo lỗi thay vì crash — xác nhận cơ chế xử lý lỗi hoạt động đúng thiết kế.

3.4. Luồng xem Dashboards (đã nối API thật)

3.4.a. Tải dữ liệu tổng hợp khi mở tab Dashboards

DashboardsScreen mở lên → dashboardsSummaryProvider (FutureProvider, không phải AsyncNotifier) → DashboardsRepository.getSummary() [lớp duy nhất state được gọi] → DashboardsRemoteDatasource.getSummary() [gọi Dio: GET /dashboards/summary] → AuthInterceptor tự gắn Bearer token (giống mọi request khác) → Backend: 3 câu SQL GROUP BY/COUNT chạy song song (severity breakdown / theo nguồn / theo ngày 7 ngày qua) ← trả JSON đã tổng hợp sẵn: {severityBreakdown, bySource, dailyTrend, topSources} ← DashboardSummary.fromJson(...) → DashboardsScreen đọc đủ 4 field, dựng lần lượt: 3 StatCard + AppPieChart, AppBarChart (theo nguồn), AppLineChart (7 ngày), AppDataTable (top nguồn)

Khác Alerts ở điểm quan trọng: Dashboards dùng FutureProvider đơn giản, không phải AsyncNotifier — vì không có tương tác nào làm đổi state sau khi tải xong (không filter, không toggle). Toàn bộ 4 panel chỉ hiển thị đúng những gì backend trả về, không tự tính toán gì thêm ở tầng app — đúng tinh thần "Dashboards chỉ XEM" đã chốt ở Phần I.

3.4.b. Vì sao tính toán ở backend, không ở app

Quyết định đã chốt qua thảo luận (không phải mặc định): backend tính sẵn severity breakdown/group theo nguồn/xu hướng theo ngày bằng SQL, trả JSON đã tổng hợp — app chỉ vẽ lại đúng số liệu nhận được, không tự groupBy/count lại từ danh sách alert thô.

Lý do: nếu app tự tính, logic thống kê sẽ nằm rải rác ở 2 nơi (app tự tính cho Dashboards, backend tính cho các mục đích khác sau này) — dễ lệch kết quả. Đặt ở backend còn cho phép tính trên toàn bộ dữ liệu thật trong DB, không giới hạn bởi số lượng alert app đã tải về.

3.4.c. Component đã chốt ghép vào màn hình

V.Hướng dẫn chạy thử

5.1. Chạy backend (bắt buộc chạy trước, mọi luồng đều cần)

  1. cd v2-mobileapp-backend
  2. npm install (chỉ cần lần đầu)
  3. npm run migrate (chỉ cần lần đầu — tạo bảng users + alerts trên Neon)
  4. npm run seed:alerts (chỉ cần lần đầu, hoặc khi muốn reset lại dữ liệu Alerts test — script tự xóa data cũ trước khi seed lại)
  5. npm run dev → server chạy ở http://0.0.0.0:3000, tự restart khi sửa code (nodemon)

0.0.0.0 thay vì localhost để Android emulator (qua địa chỉ đặc biệt 10.0.2.2) gọi vào được máy host.

5.2. Chạy app thật (Android emulator)

  1. Backend phải đang chạy (mục 5.1) trước khi mở app
  2. flutter emulators --launch Pixel_7 (hoặc emulator khác đã tạo)
  3. flutter run tại thư mục v2-mobileapp-development — mặc định chạy lib/main.dart, tức app thật (khác Widgetbook ở 5.3)
App gọi backend qua http://10.0.2.2:3000 — địa chỉ đặc biệt chỉ hiểu được bởi Android emulator, trỏ về localhost của máy chạy emulator đó. Chạy trên máy Android thật (cắm dây) hoặc iOS simulator sẽ KHÔNG gọi được backend qua địa chỉ này — cần đổi AppConfig.dev.apiBaseUrl (lib/core/config/app_config.dart) sang IP LAN thật của máy hoặc domain đã deploy.

5.3. Chạy Widgetbook (xem thử component độc lập, không cần backend/đăng nhập)

Dùng khi muốn xem/thử riêng 1 component dùng chung (xem lý do ở mục 2.2.b) mà không cần chạy cả app thật — hữu ích khi trình bày phần thiết kế UI/design system tách biệt khỏi phần luồng nghiệp vụ.

flutter run -t lib/main_widgetbook.dart -d chrome
  • Chạy trên Chrome (web) — nhanh hơn build Android, không cần emulator
  • Có thể đổi -d chrome thành thiết bị khác nếu muốn xem trên mobile
  • Sau khi thêm hoặc sửa 1 file *.usecase.dart, phải chạy lại dart run build_runner build để cập nhật main_widgetbook.directories.g.dart (file tự sinh, không sửa tay) — nếu không, use case mới sẽ không hiện trong catalog dù đã lưu file

Giao diện Widgetbook chia 2 phần: cây danh mục bên trái (theo đúng đường dẫn thư mục trong lib/widgetbook/, xem mục 2.3) và khung xem trước bên phải — có thể đổi theme sáng/tối, đổi kích thước màn hình giả lập ngay trên UI để kiểm tra responsive.

Bẫy lúc setup lần đầu (không gặp lại nếu chỉ thêm use case mới): class WidgetbookApp phải có annotation @widgetbook.App() thì mới sinh được file .directories.g.dart. Vì file đó chưa tồn tại ở lần build đầu tiên, phải tạm comment import + dùng directories: const [], build 1 lần để file được sinh ra, rồi mới mở lại import thật.

Hiện có 21 use case (mục 2.3): 19 component dùng chung + ThemeShowcase (trưng bảng màu/button/input/card) + LoginScreen (màn hình thật duy nhất có mặt trong catalog). Widgetbook tự đếm ra 24 Components • 51 Use-cases ở footer catalog vì nó gộp cả biến thể theo tham số (mỗi use case có thể là nhiều "story" nhỏ) — không phải cùng đơn vị đếm với "component dùng chung" ở đây.
